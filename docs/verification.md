## 選對測試

| 層級 | 指令與用途 |
| --- | --- |
| 靜態檢查、型別、單元 | `npm run check`：檢查格式與 JSDoc 型別，驗證 API 解析、定位、格式化、時區與本機偏好等非 DOM 邏輯。 |
| HTML 契約 | `npm test` 包含 [`tests/markup.test.js`](../tests/markup.test.js)，檢查介面 ID、CSP、相對路徑和資料來源標示。 |
| 覆蓋率 | `npm run test:coverage`：行 95%、分支 85%、函式 90%，以單元測試所載入模組的覆蓋率為準。 |
| 瀏覽器端對端 | 安裝 `npx playwright install chromium` 後執行 `npm run test:e2e`。使用本機伺服器與固定 API 測試資料，無須依賴外部天氣服務。CI 失敗時到 Actions 下載 `playwright-report`（含 trace 與截圖）。 |

單元檔案置於 `tests/**/*.test.js`，使用 `node:test` 和 `node:assert/strict`。瀏覽器案例置於 `e2e/**/*.spec.js`，API fixture 集中在 [`tests/helpers/fixtures.js`](../tests/helpers/fixtures.js)。變更回應格式，請同步更新 fixture 與解析測試，不要讓測試因即時天氣或網路狀態而失敗。

## 手動冒煙測試

1. 桌面與 360–390 px 寬度開啟本機網址，檢查主要內容、天氣狀態、逐時預報捲動及底部資料來源。重測淺／深色及減少動態效果。
2. 只用鍵盤搜尋城市，檢查焦點、方向鍵、Enter、Esc 和沒有結果時的訊息；用中文輸入法完成一次搜尋。
3. 分別允許與拒絕定位，再測逾時或不支援；確認會出現可理解的狀態。等待定位時選城市，選擇的城市應保留。
4. 在同一地點刷新、切換單位、快速切換城市、重載已選城市。模擬離線再恢復，確認更新失敗時保留的資料只屬於原地點。
5. 在正式頁面重做本次改動的關鍵操作。記錄實際測到的瀏覽器與版本；桌面瀏覽器模擬手機寬度不能替代實體 Android／iOS 的定位、觸控驗收。

## 怎麼量效能

以正式入口或相同的本機 `/time_weather/` 頁面比較。**先固定條件，再比較數字**：記錄提交、瀏覽器與版本、裝置或模擬設定、視窗尺寸、網路／CPU 限速，以及冷／暖快取是否分開。從相同的初始狀態，前後各跑至少 5 次，報中位數與範圍，不只留下最快的樣本。

| 觀察項目 | 量測方法 |
| --- | --- |
| 初次載入成本 | 用瀏覽器開發者工具 Network 記錄首載請求數、傳輸量與最大資產。應用程式資產與外部 API 分開列，冷暖快取分開量。 |
| 初次看得到主要內容 | 用 Performance 記錄 LCP 與 CLS，並註明元素、版面或字體是否不同。定位許可對話框等待不算作渲染速度。 |
| 搜尋、切換、捲動的反應 | 用同一城市與固定 API fixture 重複輸入、切換、捲動，對照主執行緒長工作和互動到畫面更新的時間。不要把單次操作計時稱作實際使用者的 INP。 |
| 等候天氣資料 | 度量「開始請求 → 收到資料」與「收到資料 → 畫面完成」兩段；合成 fixture 量測只代表相同網路條件下的程式差異。 |

PR 建議至少附「比較提交、測試頁面、條件、前後數字、可重現步驟」，並保留有關的 trace 或截圖。Lighthouse／DevTools 結果是實驗室樣本，不等同真實流量或實體裝置效能。
